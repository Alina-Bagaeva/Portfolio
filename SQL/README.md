# 1. Витрина движения и остатков денежных средств(ostatki_dds_short.sql)

SQL-запрос для ClickHouse, который формирует ежедневную витрину по движению денежных средств и остаткам.

## Что делает
- Строит календарь с `2024-12-31` по текущую дату.
- Собирает организации из остатков и движений.
- Определяет корневые статьи ДДС через иерархию.
- Формирует полный набор комбинаций: дата × организация × статья × тип операции.
- Считает поступления, выплаты и обороты по статьям ДДС.
- Восстанавливает остатки на начало и конец дня, заполняя пропуски последним известным значением.
- Возвращает `0` для отсутствующих комбинаций.

## Результат
| Поле | Описание |
|------|----------|
| `date_col` | Дата |
| `root_folder` | Корневая статья ДДС / тип остатка |
| `Organizatsiya` | Организация |
| `type_value` | Поступление, Выплата, Оборот, Остаток на начало/конец |
| `summa` | Сумма |

## Источники
- `DvizhenieDS2` — движения ДС
- `OstatkiDeneg2` — остатки ДС
- `StatiDDS_Hierarchy` — иерархия статей ДДС

## Особенности
- Для депозитов формируется отдельный расчётный счёт: `Депозит <Организация>`.
- Внутреннее перемещение ДС выделяется отдельно.
- Статьи «Госпошлина», «Движение ДС по вкладам», «Единый налоговый платёж» относятся к операционной деятельности.

# 2. Отчёт по финансовым результатам (ОФР)(OFR2_hierarcy.sql)

SQL-запрос для ClickHouse, формирующий отчёт о финансовых результатах с иерархией строк и сравнением с прошлым годом.

## Что делает
- Строит иерархию строк отчёта из `StrukturaOFR` (до 4 уровней).
- Собирает данные из множества источников: ОФР, налоги, доходы/расходы, финансовая и инвестиционная деятельность.
- Приводит все строки к единой структуре: `level1`, `level2`, `level3`, `StrokaOtcheta`.
- Исключает двойной счёт доходов (излишки, возмещения, неустойки, фин/инвест деятельность).
- Считает итоги по прибыли: отдельно доходы и расходы.
- Подтягивает сумму за аналогичный период прошлого года (`Prev_year_summa`).

## Источники
- `StrukturaOFR` — иерархия строк ОФР
- `OOFR2` — основной ОФР
- `OFR_FinDeyatelnost` — финансовая деятельность
- `OFR_InvDeyatelnost` — инвестиционная деятельность
- `DokhodyOtProdazh` — выручка
- `SsRealizovannoyProduktsii` — себестоимость
- `RaskhodyProchie` — прочие расходы
- `DokhodyProchie`, `DokhodyProchieVse` — прочие доходы
- `Nalog` — налог на прибыль

## Результат
| Поле | Описание |
|------|----------|
| `NachaloPerioda` | Начало периода |
| `KonetsPerioda` | Конец периода |
| `Organizatsiya` | Организация |
| `level1`, `level2`, `level3` | Уровни иерархии |
| `StrokaOtcheta` | Строка отчёта |
| `Summa` | Сумма |
| `Prev_year_summa` | Сумма за аналогичный период прошлого года |

## Особенности
- Доходы по банковским вкладам относятся к финансовой деятельности.
- Расходы по лизингу относятся к инвестиционной деятельности.
- Итоги по прибыли формируются отдельными строками: `Итого прибыль / Доходы` и `Итого прибыль / Расходы`.
- Для отсутствующих данных прошлого года возвращается `0`.

# 3. Розница: анализ первой продажи по папкам номенклатуры(Retail_depth_only_initial_purchases.sql)

SQL-запрос для анализа поведения клиентов, купивших розничные лицензии: определяет, когда у клиента появилась первая продажа по каждой группе номенклатур относительно первой розничной покупки.

## Что делает
1. **Строит дерево папок** рекурсивно от корневой папки `01 Лицензии СБиС` (id = 19652), до 4 уровней вложенности, с полным путём в `JSON`-массиве.
2. **Определяет номенклатуры** внутри дерева и их папку второго уровня.
3. **Находит первую розничную покупку** каждого клиента (`Retail_Cash`, `RETAIL`, `Retail_Account`) и тип лицензии.
4. **Находит первую не-розничную продажу** по каждой папке второго уровня для каждого клиента.
5. **Сравнивает даты**: продажа была `before` / `after` / `same_date` относительно первой розничной, и считает разницу в месяцах.

## Логика расчёта `month_diff`
- Если первая розничная и первая продажа в папке попали в **один календарный месяц** → `0`.
- Если продажа в папке раньше розничной → отрицательное значение.
- Если позже → положительное.
- Сравнение идёт по началу месяца (`%Y-%m-01`).

## Результат
| Поле | Описание |
|------|----------|
| `taviat_client_id` | ID клиента |
| `first_ritail_sale` | Дата первой розничной покупки |
| `first_ritail_license` | Тип первой розничной лицензии |
| `folder` | Папка второго уровня |
| `first_sale_date` | Дата первой продажи в папке |
| `before_after` | `before` / `after` / `same_date` |
| `month_diff` | Разница в месяцах (со знаком) |
| `row_id` | Уникальный номер строки |

## Особенности
- Учитываются только отгрузки (`shipment = 1`), неудалённые (`deleted = 0`) и завершённые документы.
- Глубина дерева папок ограничена 4 уровнями.
- Розничные позиции исключаются из анализа «первой продажи по папке».
- Используется `WITH RECURSIVE` для обхода иерархии папок.

# 4. Сводный отчёт по сотрудникам: финансы и активность в чатах

SQL-запрос для ClickHouse/MySQL, объединяющий финансовые показатели сотрудников (счета, платежи, возвраты) с их активностью в чатах и сообщениях.

## Что делает

### Финансовая часть
1. **Объединяет платежи** из двух источников:
   - напрямую привязанные к исходящим счетам (`outbill`),
   - через реализации (`realization`), связанные со счетами.
2. **Разделяет потоки** на выручку (`sum > 0`) и возвраты (`sum < 0`).
3. **Агрегирует счета** (`outbill`): количество и сумма выставленных счетов по дням и сотрудникам.
4. **Сводит всё вместе** в единую таблицу по дням и сотрудникам.

### Чаты и сообщения
5. **Единое чтение** таблицы сообщений (`sbis_channel_chat_messages`) — только сообщения сотрудников (не клиентов), обычные и аудио.
6. **Агрегирует сообщения** по дням и сотрудникам.
7. **Агрегирует чаты** по месяцам (дата = первое число месяца).

### Объединение
8. **Финальный `UNION ALL`** из трёх частей:
   - финансы (дни),
   - сообщения (дни),
   - чаты (месяцы, с заглушками в финансовых полях).

## Результат
| Поле | Описание |
|------|----------|
| `date_col` | Дата (для чатов — первое число месяца) |
| `employee_name` | ФИО сотрудника |
| `count_outbills` | Кол-во выставленных счетов |
| `outbill_summ` | Сумма счетов |
| `count_payments` | Кол-во оплаченных документов |
| `revenue` | Выручка (входящие платежи) |
| `count_returns` | Кол-во возвратов |
| `returns` | Сумма возвратов |
| `count_chats` | Кол-во уникальных чатов (за месяц) |
| `count_messages` | Кол-во сообщений (за день) |

## Особенности
- Платежи через реализации подтягивают ответственного **из связанного счёта**, а не из реализации.
- Учитываются только проведённые документы (`completed_status > 0`) и неудалённые (`deleted = 0`).
- Сообщения клиентов исключаются (`message_type != 'client'`).
- Для несоответствия сотрудника в чатах — имя `'Не известен'`.
- Чаты выводятся с датой первого числа месяца, чтобы совместить с дневной гранулярностью финансов и сообщений.
